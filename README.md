# kip-sensors

Учебное CLI-приложение на Rust для ведения каталога промышленных датчиков КИПиА. Проект развивается небольшими шагами: **модель → правила → тесты → CLI → постоянное хранение**.

> Состояние проекта: 10 октября 2026 года. SQLite подключён, схема создаётся и проверяется тестом. Сохранение и загрузка самих датчиков пока в разработке.

## Зачем проект

Практически изучить Rust на понятной предметной области: ownership, borrowing, `enum`, `Option`, `Result`, обработку ошибок, модули, тестирование и взаимодействие с SQLite. Код должен объяснять себя именами, а публичный API дополняется `///`-документацией.

## Что уже реализовано

### Предметная модель: `sensor.rs`

- Создание `Sensor` с проверкой непустого имени и расположения.
- Доступ на чтение к `id`, `name`, `location`, `status`.
- Изменение имени (`rename`), места (`relocate`) и статуса.
- Типизированные ошибки `SensorError`; статусы `SensorStatus`.

### Каталог: `catalog.rs`

- `SensorCatalog::new()` и `Default` создают пустой каталог.
- `add()` не допускает повторный ID и возвращает `Result<(), CatalogError>`.
- `find()` возвращает `Option<&Sensor>`; `find_mut()` возвращает `Option<&mut Sensor>`.
- `sensors()` возвращает срез `&[Sensor]`; `remove()` удаляет и возвращает `Option<Sensor>`.

### Командная строка: `cli.rs` + `main.rs`

Парсер преобразует пользовательские строки в типизированный `Command` и сообщает конкретные ошибки через `Result<Command, CliError>`.

```bash
cargo run -- list
cargo run -- show 2
cargo run -- remove 2
cargo run -- add 4 PT-404 "Гомогенизатор, линия 1"
```

**Важно:** сейчас тестовые датчики каждый раз заново создаются в `main.rs`. Изменения команды `add`/`remove` пока не переживают следующий запуск. Наличие файла SQLite само по себе этого не меняет.

### Хранение: `storage.rs`

- `rusqlite` открывает SQLite-файл или временную базу `:memory:`.
- Схема загружается через `include_str!` и применяется с `execute_batch`.
- Таблица `sensors` содержит `id`, `name`, `location`, `status`; `id` уникален, допустимые статусы ограничены `CHECK`.
- Запись `INSERT`, чтение `SELECT` и синхронизация CLI с БД ещё **не реализованы** на этом контрольном этапе.

## Проверки

```bash
cargo fmt --check
cargo test
cargo clippy --all-targets
```

На этом этапе: **23 unit-теста** (`src/lib.rs`) и **1 integration-тест** (`tests/catalog_flow.rs`) проходят. Doc-тестов пока нет.

Для проверки SQLite при наличии системной утилиты `sqlite3` и файла `sensors.db`:

```bash
sqlite3 sensors.db '.schema sensors'
```

Локальный `sensors.db` и его служебные файлы должны быть в `.gitignore`; в Git храним исходный SQL, а не рабочую базу.

## Учебный маршрут и ключевые понятия

| Этап | Что сделали | Что изучили |
| --- | --- | --- |
| 1. Модель | `Sensor`, `SensorStatus`, `SensorError` | `struct`, `enum`, `impl`, `String`, `&str` |
| 2. Правила | Проверки и операции над датчиком | `Result`, `Option`, `match`, `&self`, `&mut self` |
| 3. Каталог | Добавление, поиск, удаление, запрет дублей | `Vec`, итераторы, `any`, `find`, `position`, move/Copy |
| 4. Тесты | Unit- и integration-тесты | `#[cfg(test)]`, `#[test]`, `assert_eq!`, публичный API |
| 5. Библиотека | Выделили `lib.rs` | crate, модули, `pub`, импорты |
| 6. CLI | Разбор `list`, `show`, `remove`, `add` | `std::env::args`, `collect`, `let else`, `?`, `ok_or`, `map_err` |
| 7. SQLite: основа | Подключение и начальная схема | `rusqlite::Connection`, `include_str!`, `execute_batch`, `:memory:` |

### Принципы проекта

1. Публичные типы, функции и важные ошибки документируем через `///`.
2. Комментарий поясняет **причину** неочевидного решения, а не пересказывает строку кода.
3. Сначала небольшой тестируемый контракт; затем его использование в `main.rs`.
4. Не применяем `.clone()` без объяснимой потребности во владении.
5. Домен не должен зависеть от конкретного интерфейса пользователя.
6. Коммиты делаем по учебным вехам; каждый коммит должен собираться и проходить тесты.

## Как обновлять журнал

После учебного этапа обновить таблицу маршрута и ближайшие шаги, выполнить `cargo test`, посмотреть `git diff`, затем сделать отдельный Git-коммит с понятным сообщением. История Git хранит **как менялся код**, этот файл хранит **почему и чему мы научились**.
